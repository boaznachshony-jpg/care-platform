## 1. בשורה אחת

השורות של הדוח החודשי לביטוח לאומי עוברות מהגוש הכללי שמסונכרן מהדפדפן לטבלה ייעודית
בשרת, תחת תיק ההעסקה — **בהעתקה, לא בהעברה**: העותק הישן נשאר במקומו עד שמוכח שכל שורה
הגיעה.

## 2. מה קיים היום

| | |
|---|---|
| **מה נשמר** | לכל תשלום ביטוח לאומי: שורה לכל חודש — `month`, `employed`, `wage` (שקלים שלמים, כמו בטופס המוסד), `ratePercent`, `amount` |
| **איפה** | `MvpEmploymentExpense.nationalInsuranceMonths` ב-`apps/web/src/storage/mvp-storage.ts`, בתוך המפתח `caredesk.mvp.employment-expenses.v1::<clientId>` של ה-workspace |
| **איך מגיע לשרת** | כחלק מגוש ה-workspace כולו (`tenant_workspace.payload`), מוצפן ב-AES-256-GCM. השרת אינו "רואה" את השורות כנתון בפני עצמו |
| **ממתי** | מאז פריסת L (PR #145, 17.10.2026). **לפני כן השורות נזרקו**, כך שאין שורות ישנות יותר לשמר |
| **מעמד** | חריגה מתועדת ומאושרת מ-ADR-006 סעיף 5, עם תנאי הסרה: הטבלה שבמסמך הזה |

## 3. מה לא משתנה

- **החישוב** — אותן נוסחאות, אותם סכומים, אותו מסך.
- **התשלום עצמו** (הסכום, מועד היעד, "שולם") נשאר ב-workspace. R5-09 עוסק רק בשורות
  הדוח. בית קנוני להוצאות התקופתיות הוא פריט נפרד, שלא נפתח כאן.
- **שום נתון אינו נמחק** בשום שלב של המסמך הזה. גם לא העותק הישן — ראה §5.

## 4. מבנה הטבלאות

שתי טבלאות: **דוח** (אחד לכל תשלום) ו**שורות** (אחת לכל חודש בדוח).

**למה שתיים ולא אחת לפי חודש:** היום אפשר שיהיו שני תשלומים שמכסים אותו חודש — למשל
התשלום שנוצר אוטומטית מהשכר ותשלום ביטוח לאומי שהוזן ידנית. טבלה אחת עם "חודש אחד = שורה
אחת" הייתה מכריחה לבחור ביניהם בזמן ההעתקה, כלומר לזרוק אחד. שתי טבלאות שומרות את שניהם
כמו שהם, ובדיקה נפרדת יכולה להתריע "חודש דווח פעמיים" בלי לאבד דבר.

### `national_insurance_report` — דוח

| עמודה | סוג | הערה |
|---|---|---|
| `id` | uuid | |
| `tenant_id` | uuid | בלתי ניתן לשינוי; RLS |
| `employment_case_id` | uuid | FK מורכב `(tenant_id, employment_case_id)` → `employment_case` — דוח לא יכול להצביע על תיק של משפחה אחרת |
| `period_start`, `period_end` | date (ה-1 בחודש) | החודש הראשון והאחרון שהדוח מכסה. `period_start <= period_end` |
| `due_date` | date | מועד התשלום, כפי שנשמר עם התשלום |
| `legacy_expense_id` | text, nullable | מזהה התשלום ב-workspace שממנו הועתק. נכתב פעם אחת. ייחודי לתיק (partial unique index) — זה מה שהופך העתקה חוזרת לבטוחה |
| `sensitivity` | text | קבוע `financial_sensitive` (שכר) |
| `created_at/by`, `updated_at/by`, `version` | | העמודות הסטנדרטיות של `docs/architecture/database-blueprint.md` §3 |

### `national_insurance_report_month` — שורה

| עמודה | סוג | בדיקה במסד |
|---|---|---|
| `id`, `tenant_id` | uuid | |
| `report_id` | uuid | FK מורכב `(tenant_id, report_id)` → הדוח |
| `month` | date (ה-1 בחודש) | ייחודי בתוך הדוח: `unique (report_id, month)` |
| `employed` | boolean | |
| `wage` | integer | שקלים שלמים, `0..10,000,000` |
| `rate_percent` | numeric(5,2) | `0..100` |
| `amount` | numeric(12,2) | `0..10,000,000`; ההמרה לאגורות דרך `caredesk_agorot()` (מיגרציה 0045), כמו בשאר טבלאות הכסף |
| | | **`employed = false` ⇒ `wage = 0` ו-`amount = 0`** — בדיוק מה שהמסך מייצר היום |
| `created_at/by`, `updated_at/by`, `version` | | |

**כללים לשתי הטבלאות** (כמו `medication`, מיגרציה 0046):
- `enable` + `force row level security`, ומדיניות בידוד לפי `app.tenant_id`.
- הרשאות `select, insert, update` בלבד לתפקיד האפליקציה. **אין `delete`** — דוח שהוגש
  אינו נמחק; תיקון הוא עדכון, שנרשם ב-`audit_event`.
- השרת **מחשב מחדש** `wage × rate` באגורות ודוחה שורה שהסכום שלה אינו תואם (כמו DOM-02
  בסגירת חודש). השורות של L חושבו באותה נוסחה בדיוק, ולכן צפויות לעבור; שורה שנדחית —
  ראה §7.

## 5. איך עוברים בלי לאבד נתונים — ארבעה שלבים

כל שלב הוא PR נפרד. **בכל רגע יש בדיוק מקום אחד שהוא מקור הכתיבה** (ADR-006 סעיף 6).

### שלב 1 — הטבלה והשרת (המיגרציה)
- מיגרציה `0049`: שתי הטבלאות בלבד. additive — אינה נוגעת בשום טבלה קיימת.
- נתיבי API: `GET /cases/:caseId/national-insurance-reports` ו-
  `POST /cases/:caseId/national-insurance-reports/import`.
- **אף מסך עוד לא קורא ולא כותב.** המשתמש לא רואה דבר.
- **מקור הכתיבה:** ה-workspace, כמו היום.
- **דורש:** אישורך המפורש ל-PR הזה (מיגרציה).

### שלב 2 — העתקה ברקע
- במסך השכר של לקוח שמקושר לתיק העסקה, הדפדפן שולח כל תשלום שיש לו שורות אל `import`,
  אחד אחד — **אותו מנגנון שהעביר משימות, מסמכים ותרופות** (`apps/web/src/sync/legacy-upload.ts`).
- ההעתקה רצה **רק אחרי שה-workspace נטען מהשרת בסשן הנוכחי**, כדי שמכשיר לא ישלח עותק
  מקומי ישן (§7).
- **העתקה חוזרת בטוחה:** אותו `legacy_expense_id` לא ייצור דוח שני (מאוכף במסד). אם
  השורות במכשיר השתנו מאז, הדוח בשרת מתעדכן ומקבל `version` חדש ורישום ב-audit.
- **העותק ב-workspace אינו נמחק ואינו משתנה.** ההעתקה היא תוצאת לוואי בלבד.
- **כשל נראה על המסך** (CLAUDE.md §2) — באותה צורה שבה כשל העלאה של משימה מוצג היום.
- לקוח **שאינו מקושר** לתיק (`employment_case.legacy_client_id` ריק): לא מועתק דבר. השורות
  נשארות ב-workspace בדיוק כמו היום, והבאנר הקיים "לא נפתח עדיין תיק העסקה קנוני" נשאר.
- **מקור הכתיבה:** עדיין ה-workspace. השרת מחזיק עותק.

### שלב 3 — המעבר
- תנאי כניסה: **מדידה** שכל שורה ב-workspace קיימת בשרת עם אותם ערכים (§6), לכל הדיירים.
- שמירת דוח במסך השכר כותבת **לשרת**, והפתיחה לעריכה קוראת **מהשרת**.
- ה-workspace מפסיק לקבל שורות חדשות; השורות שכבר שם **נשארות** כעותק היסטורי שניתן לשחזר.
- **מקור הכתיבה:** השרת.
- המעבר הפיך: אם מתגלה בעיה, מחזירים את הקריאה ל-workspace — השורות שם לא נגעו.

### שלב 4 — סגירת החריגה
- תנאי כניסה: שלב 3 רץ בייצור **30 יום** בלי פער במדידה, **ותרגיל שחזור עבר בהצלחה**
  (`docs/governance/RESTORE-DRILL.md` — נכון לכתיבת המסמך הוא לא הורץ מעולם).
- מוחקים **מהקוד** את השדה `nationalInsuranceMonths`, את `MvpNationalInsuranceReportMonth`
  ואת רשומת ה-`exceptions` ב-`scripts/adr-006-freeze-baseline.json` — תנאי ההסרה של
  amendment 1.
- הגרסאות הישנות של ה-workspace (`tenant_workspace_history`, מיגרציה 0035) עדיין מכילות את
  השורות, ולכן גם אחרי השלב הזה אפשר לשחזר.

## 6. למה העתקה מהדפדפן, ולא העברה אחת בשרת

| | העתקה מהדפדפן (מוצע) | העברה בשרת |
|---|---|---|
| קריאת הגוש המוצפן | הדפדפן כבר מחזיק את הנתונים פתוחים | השרת צריך לפענח את ה-workspace של כל לקוח בבת אחת |
| שיוך לתיק | הדפדפן יודע לאיזה לקוח שייך כל תשלום, ומסך השכר כבר מאתר את התיק | מיפוי `clientId → employment_case` לכל דייר, בתוך סקריפט |
| עבודה על מסד הייצור | כל לקוח לבדו, דרך אותם נתיבים ואותן הרשאות של המוצר | ריצה אחת על כל הלקוחות |
| ניסיון קודם | עבד למשימות, מסמכים ותרופות (PR #120) | לא נעשה במוצר |
| חיסרון | לקוח שלא נכנס למסך השכר לא מועתק | — |

החיסרון אינו אובדן: מי שלא הועתק, השורות שלו נשארות ב-workspace בדיוק כמו היום. המדידה
של שלב 3 מראה כמה כאלה יש, ושלב 3 לא מתחיל לפני שהמספר הוא אפס.

**המדידה עצמה** מתבצעת בשרת וקוראת בלבד: הסריקה הלילית (מיגרציה 0038,
`packages/db/src/tenant-census-repository.ts`) כבר פותחת את ה-workspace המוצפן כדי לספור
רשומות. נוסיף לה ספירה של שורות ביטוח לאומי ב-workspace מול שורות בטבלה, לכל דייר. היא
סופרת בלבד — אינה מעתיקה ואינה כותבת נתוני לקוח.

## 7. מה יכול להשתבש, ומה קורה אז

| מקרה | מה קורה |
|---|---|
| ההעתקה נכשלת (רשת, שרת) | השורות נשארות ב-workspace; הודעה על המסך; ניסיון חוזר בכניסה הבאה |
| השרת דוחה שורה (סכום לא תואם, ערך מחוץ לטווח) | אותו דבר — **התשלום כולו לא מועתק**, הדחייה נראית על המסך ונספרת במדידה. אין העתקה חלקית של דוח |
| שני מכשירים מעתיקים במקביל | המסד מקבל דוח אחד (`legacy_expense_id` ייחודי); השני מקבל את הקיים |
| מכשיר עם עותק ישן מעתיק אחרי מכשיר עדכני | ה-workspace מסונכרן עם בדיקת גרסאות (`apps/web/src/storage/workspace-sync.ts`), כך שמכשיר ישן אינו יכול לדרוס גרסה חדשה **בגוש**. אבל מכשיר יכול להציג עותק מקומי לפני שסיים לטעון מהשרת. לכן **כלל בשלב 2: ההעתקה רצה רק אחרי שה-workspace נטען מהשרת בסשן הנוכחי.** הסיכון השארי — דוח שמתעדכן לגרסה קודמת — נרשם ב-audit וניתן לתיקון; אף שורה לא נמחקת |
| חודש דווח בשני תשלומים | שניהם נשמרים. ההתרעה על כפילות היא שיפור נפרד |
| תקלה אחרי המעבר (שלב 3) | מחזירים את הקריאה ל-workspace; השורות שם לא שונו |

## 8. מה נדרש ממך

1. **אישור המבנה** — שתי טבלאות (דוח + שורות), עם `legacy_expense_id` ובלי מחיקה.
2. **אישור הדרך** — העתקה מהדפדפן (§6), לא העברה בשרת.
3. **תנאי המעבר** — מה נחשב "תקופה מוסכמת" בשלב 4 (הצעה: 30 יום בלי פער במדידה), ושתרגיל
   השחזור הוא תנאי לשלב 4. **אושר: 30 יום בלי פער, ותרגיל שחזור שעבר.**
4. **אחר כך, בנפרד:** אישור מפורש ל-PR של המיגרציה (שלב 1) כשיהיה מוכן.
